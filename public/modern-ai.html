Part II

Transformers, LLMs and Agents

Almost everything called "AI" today is one architecture, trained one way, wrapped in one of a few patterns. This part follows the chain from a character of text to a system that can act: how text becomes numbers, what a transformer does with them, how a language model is trained and run, and what has to be built around it before it can do anything on your behalf.

Neural Networks and Deep Learning

Key idea

A neural network is a stack of simple linear steps separated by a non-linearity — and depth is what lets later layers build on what earlier ones found.

The unit of a neural network is deliberately unimpressive. It takes some numbers in, multiplies each by a weight, adds a bias, and passes the total through a non-linear activation function — most often ReLU, which simply replaces negatives with zero. Thousands of these arranged in layers, and the whole thing becomes a general-purpose function approximator.

The non-linearity is not decoration. Without it, a stack of linear layers collapses algebraically into a single linear layer, and a hundred layers would be exactly as expressive as one. The activation function is what makes depth mean anything.

Running data through the network is the forward pass: values enter at the input layer, each layer transforms them, and the output layer produces a prediction. Training runs the same machinery backwards. A loss function scores the prediction; backpropagation applies the chain rule layer by layer to work out how much each individual weight contributed to that error; gradient descent nudges every weight accordingly. That is the entire training loop, repeated over batches for many passes through the data.

"Deep" just means many layers, and depth buys hierarchy. In a vision network, early layers respond to edges, middle layers to shapes and textures, late layers to whole objects. In a language model, early layers deal in surface patterns — spelling, morphology — and later layers in syntax, reference and meaning. Nobody designs that hierarchy; it falls out of training a deep enough network on enough data.

Tokens and Embeddings

Key idea

A model never sees text. It sees integers that index a table of learned vectors, in a space where nearness means "used in similar ways".

Before any of the interesting machinery runs, text has to become numbers, and that happens in two steps.

The first is tokenization. Text is chopped into tokens — usually sub-word units chosen by an algorithm such as byte-pair encoding, which starts from characters and repeatedly merges the most frequent adjacent pair. The effect is that common words end up as a single token while rare ones split into pieces, so the vocabulary stays a fixed size (typically 50,000–200,000 entries) and no input is ever out-of-vocabulary. As a rule of thumb, one token is about four characters of English, or three-quarters of a word. Tokens are also the unit in which context limits are measured and inference is billed, which is why the concept leaks out of the architecture and into pricing pages.

Tokenization explains a family of otherwise baffling model failures. Counting the letters in a word is hard for a model that never saw letters; arithmetic is uneven because numbers split into token chunks inconsistently; and languages that tokenize inefficiently cost more per sentence.

The second step is the embedding. Each token id indexes a row of a large learned matrix, retrieving a vector of hundreds or thousands of numbers. That vector is the model's entire starting representation of the token, and — crucially — it is learned during training rather than designed.

What makes embeddings useful is that the geometry ends up meaningful. Tokens used in similar contexts land near each other, so distance approximates similarity. Directions carry relationships too: the classic demonstration is that the offset from man to king is roughly the offset from woman to queen. Real embedding spaces are messier than the textbook picture, but the intuition holds, and it is exactly what makes embeddings the substrate for semantic search, clustering, deduplication and the retrieval systems later in this part.

One thing embeddings do not carry is position. Attention, as the next chapter shows, is order-blind by construction, so position has to be injected separately — as fixed sinusoidal patterns in the original transformer, and as rotary position embeddings (RoPE) in most current models.

The Transformer Architecture

Key idea

Each layer does two things: let the tokens exchange information, then think about each token on its own. Stack that block enough times and you have a language model.

The transformer arrived in 2017 in a paper titled Attention Is All You Need, and it replaced the recurrent networks that had dominated sequence modelling. The reason was less about accuracy than about hardware. A recurrent network reads a sequence one token at a time, each step waiting on the last — inherently sequential, and therefore slow to train. A transformer processes every position of the sequence simultaneously. That maps cleanly onto GPUs, and it is the reason training at today's scale became possible at all.

The architecture is a single block repeated. Each block has two sub-layers:

  • Multi-head self-attention — the only place where information moves between positions. Each token gathers what it needs from the other tokens.
  • A feed-forward network — a small two-layer network applied to each position independently and identically. This is where most of the parameters live, and the current best guess is that it is where most factual knowledge is stored.

Each sub-layer is wrapped in two things that are easy to overlook and essential in practice. A residual connection adds the sub-layer's input back to its output, giving gradients a short path all the way down a very deep stack — without it, networks this deep do not train. And layer normalisation rescales activations to keep them in a stable range as they pass through dozens of blocks.

After the last block, a final normalisation and a linear projection map each position's vector to one score per vocabulary entry, and a softmax turns those scores into probabilities. The number of blocks is the model's depth: 12 in the smallest GPT-2, of the order of a hundred in frontier models. Same shape every time, different learned weights.

Three variants are worth being able to tell apart. Encoder-only models such as BERT see the whole sequence at once in both directions and are used for classification and embeddings. Decoder-only models — the GPT family and essentially every chat model — see only the tokens before each position, which is what makes generation possible. Encoder-decoder models such as T5 read one sequence and write another, the natural shape for translation.

Attention, Step by Step

Key idea

Every token asks a question, every token advertises what it has, and each one rebuilds itself out of a weighted blend of the answers.

Attention is the mechanism that lets "it" in the cat sat on the mat because it was warm resolve to the mat. It works in four steps.

1. Three projections. From each token's vector the layer computes three new vectors using learned weight matrices: a query (what this token is looking for), a key (what it offers to others), and a value (what it actually contributes if selected).

2. Score. The dot product of one token's query with every token's key gives a raw relevance score for each pairing. The scores are divided by the square root of the key dimension, which keeps them from growing so large that the next step saturates.

3. Normalise. A softmax across each row turns those scores into weights that sum to one — a distribution over "how much of my new representation should come from each other token".

4. Mix. The output for a position is the weighted sum of every token's value vector. A token has now built a representation of itself that includes whatever context it decided was relevant.

Two refinements turn this into what models actually run.

Multi-head attention runs the whole operation several times in parallel with different projection matrices, then concatenates the results and projects them back down. Each head is free to specialise, and in practice they do — some track syntactic dependencies, some track coreference, some mostly attend to the previous token. One attention pattern per layer would be a severe bottleneck; frontier models run tens of heads per layer.

Causal masking is what makes generation work. In a decoder-only model a token may attend only to itself and the tokens before it; scores for future positions are set to negative infinity before the softmax, so their weights come out at zero. This is what allows a model to be trained on every position of a sequence at once — each position is predicting its own next token without being able to peek at the answer.

The cost of all this is the defining constraint of the architecture. Every token is compared with every other token, so the work grows with the square of the sequence length. Doubling the context length quadruples the attention computation. That single fact drives most of the engineering around long context: the KV cache that stores past keys and values so they are not recomputed for every generated token, memory-efficient implementations such as FlashAttention, and approximations like sliding-window and grouped-query attention.

Large Language Models

Key idea

An LLM is a large transformer trained on one absurdly simple objective — predict the next token — and then shaped by further training into something worth talking to.

Training happens in stages, and they do genuinely different jobs.

Pretraining runs the model over trillions of tokens of text with a single objective: given everything so far, predict what comes next. The objective is trivial; doing it well is not. To predict the next token in a proof you need arithmetic, in a stack trace you need to know the language, in a dialogue you need to model what a person would plausibly say. Capability arrives as a side effect of compression. And because the label is just the next token already present in the text, no human annotation is required — which is what allows the data to be this large.

Instruction tuning then fine-tunes on a much smaller, curated set of prompt-and-response pairs. A pretrained model will happily continue your question with three more questions, because that is what a document containing questions tends to do. This stage teaches the format of being an assistant.

Preference tuning is the last shaping step. Humans — or models trained to imitate them — rank candidate responses, and that ranking signal is used to tune the model, either through reinforcement learning against a learned reward model (RLHF) or directly (DPO). This is where an assistant learns to be helpful rather than merely plausible, to refuse sensibly, and to say it does not know.

At inference time the model runs autoregressively: it produces a probability distribution over the whole vocabulary, one token is chosen from it, that token is appended to the input, and the process repeats. Temperature and top-p control how the choice is made — at temperature zero the most likely token always wins and output is near-deterministic; higher values flatten the distribution and admit more variety. There is no separate "planning" phase. The text is produced one token at a time, left to right, and the model's only means of working something out before answering is to write tokens that do that work — which is precisely what reasoning models are trained to do at length before committing to a reply.

That context box has a hard limit: the context window, measured in tokens and covering the prompt plus everything generated so far. Modern windows are large — hundreds of thousands of tokens — but they are not memory. Nothing persists between separate calls unless a system explicitly puts it back in. Every product feature that feels like memory is a system re-assembling context behind the scenes.

Two more things worth internalising. Performance improves with parameters, data and compute in a relationship regular enough to be called scaling laws, which is why the field has been able to plan capability increases rather than stumble on them. And a second axis has opened up: spending more compute at inference time, letting a model reason at length before answering, buys accuracy on hard problems without changing the weights at all.

AI Agents

Key idea

An agent is a loop. The model chooses an action, something else executes it, the result comes back as new context, and it goes round again until the goal is met.

A chatbot is one call: text in, text out. An agent puts that call inside a loop and gives it hands. The difference in capability is large, and so is the difference in what can go wrong.

The parts are always roughly the same:

  • A goal — what the user actually wants, which the agent has to keep referring back to as the context fills up with intermediate work.
  • The model as a policy — at each step it reads the goal and the history and decides what to do next.
  • Tools — functions the model can call, each described by a schema of name, purpose and parameters. Search, code execution, file reads and writes, database queries, HTTP requests.
  • An executor — the runtime that actually performs the call and hands the result back as an observation. The model never touches anything itself; it emits a structured request and something else decides whether to honour it.
  • Memory — short-term is simply the context window; long-term is whatever the system writes down and retrieves later, such as files or a vector index.
  • A stopping condition — a step budget, a token budget, or a check that the goal is done. Without one, a confused agent will keep going.

The loop itself — reason about the state, take an action, observe the result, repeat — was popularised as ReAct, and interleaving reasoning with acting matters: a model that plans and acts in the same breath can correct itself when an observation contradicts what it expected.

Longer tasks add two more patterns. Planning breaks a goal into subtasks up front and re-plans when reality disagrees. Sub-agents hand a scoped piece of work to a fresh context and return only the conclusion, which keeps the main context from filling with intermediate noise — the same reason you would not paste an entire build log into a design discussion.

The failure modes are specific enough to design against. Agents loop without terminating; small errors compound over many steps because each observation is generated from a slightly wrong state; and untrusted tool output can carry prompt injection, where text fetched from a web page is treated as instructions rather than data. The mitigations are unglamorous and effective: hard step and token budgets, least-privilege tool scopes, sandboxes for code execution, human approval before anything irreversible, and a separate verification step rather than trusting the agent's own report that it succeeded.

Retrieval-Augmented Generation

Key idea

Don't hope the answer is in the weights. Go and find the relevant text first, and put it in the context.

A model's knowledge is frozen at training time, blurry in the details, and contains nothing about your private documents. Retraining to fix that is expensive and does not suit facts that change weekly. Retrieval-augmented generation takes the other route: look the answer up, then ask the model to write using what was found.

It runs in two phases. Indexing happens once: documents are split into chunks, each chunk is embedded into a vector, and the vectors are stored alongside their text in an index. Answering happens per question: the question is embedded with the same model, the nearest chunks are retrieved by vector similarity, and those chunks are pasted into the prompt above the question.

Whether a RAG system works comes down to unglamorous details. Chunking has to respect structure — splitting mid-sentence or mid-table destroys the meaning you are trying to retrieve. Pure vector search misses exact identifiers, part numbers and rare terms, so production systems usually combine it with keyword search and then re-rank the combined results with a slower, more accurate model. And the index goes stale silently: nothing about a wrong answer tells you the source document changed last month.

The failure to watch for is a model that is handed the right context and ignores it, answering from its weights instead. That is why asking for citations is worth the tokens: it makes the difference between a grounded answer and a fluent guess visible. Evaluate the two halves separately — did retrieval surface the right chunk, and did the model use it — because fixing the wrong half is the most common way these projects stall.

In an agent, retrieval stops being a fixed pipeline and becomes just another tool: the model decides when to search, what to search for, and whether the results were good enough to search again.

Where These Systems Break

Key idea

Every limitation below follows from the architecture, not from the model being insufficiently trained. Knowing which is which tells you what to build around.

A model that predicts plausible next tokens will produce plausible text whether or not it has grounds for it. That is not a bug that gets patched; it is what the objective asks for, and it is why the engineering around a model matters as much as the model.

Failure Why it happens What actually helps
Hallucination The objective rewards plausible continuations, not true ones. There is no internal fact store to consult. Retrieval with citations; asking for sources; letting the model verify with a tool instead of recalling.
Losing the middle Attention spreads thin over a long context, and material buried in the middle gets less weight than either end. Put the important material at the start or end; retrieve less and better; break work into scoped sub-tasks.
Prompt injection Instructions and data arrive as the same stream of tokens, so text from a web page can read as a command. Treat all tool output as untrusted; least-privilege tool scopes; confirmation before irreversible actions.
Non-determinism Sampling is stochastic, and even at temperature zero, batching and hardware make outputs vary slightly. Test against a fixed evaluation set rather than a single example; assert on structure, not exact strings.
Compounding error In an agent loop, each step conditions on the last, so a small early mistake is built upon rather than corrected. Step budgets; independent verification of the result; checkpoints a human can inspect.
Stale knowledge Weights are frozen at the training cut-off and know nothing published since. Retrieval or a search tool; stating the cut-off; never using the weights for anything time-sensitive.
Inherited bias Training data reflects the world as written, including its skews, and the model reproduces them fluently. Evaluate across affected groups specifically; measure outcomes rather than trusting intent.

Which leaves evaluation, the part most projects skip and then regret. The discipline from Part I transfers directly: a held-out set of real cases with known good outcomes, scored the same way every time, so a change can be shown to be an improvement rather than assumed to be one. Vibes do not survive contact with the fiftieth prompt tweak.

What changes is that outputs are open-ended, so scoring is harder. Anchor on whatever is checkable — did the code run, was the cited passage actually in the source, does the JSON parse, is the number right. Use a model as a judge for the rest if you must, but calibrate it against human ratings first, because an unchecked judge just moves the trust problem somewhere less visible.

None of this is a reason for pessimism about the technology. It is the ordinary situation of building on a component with known characteristics: the failures listed above are predictable, which means they are designable-around, which is most of what the work consists of.
